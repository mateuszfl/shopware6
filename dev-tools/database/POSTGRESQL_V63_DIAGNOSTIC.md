# V6_3 PostgreSQL diagnostic batch

**Diagnostic only. This is not a production-ready PostgreSQL migration port.**

The diagnostic run created registry mappings for all 335 Core V6_3 migrations. It retains 170 existing PostgreSQL variants and 9 audited same-class mappings. It generated 156 best-effort diagnostic variants. The generator flagged unhandled SQL or runtime shapes in 148 of those classes; the remaining 8 have no detected flags but are still unverified. SQLGlot was not invoked.

The first observed PostgreSQL run stopped in `Migration1574695657ProductCrossSelling` with SQLSTATE `42601` at `ENGINE=InnoDB`, after 173 migrations had completed. The refreshed diagnostic output applies CREATE TABLE rules: `BINARY(16)` columns become `BYTEA` with an `octet_length(...)=16` check; `TINYINT[(n)]` becomes `SMALLINT`; `DATETIME[(n)]` becomes `TIMESTAMP[(n)] WITHOUT TIME ZONE`; utf8mb4 column collations become `sw_type_ci`; table-level utf8mb4 defaults are copied to text columns as `COLLATE "sw_type_ci"`; and trailing MySQL engine/charset/collation options are removed. This batch copied the default collation to 31 text columns before stripping the MySQL options. It also rewrites standalone `ALTER TABLE ... DROP FOREIGN KEY <name>` statements to `DROP CONSTRAINT`, preserving identifier quoting and statement order; the latest batch matched 19 clauses in 15 classes. Multiple `DROP FOREIGN KEY` actions in one ALTER remain unchanged and now receive a specific warning: splitting them would change statement atomicity and could leave only some constraints dropped after an error. `DROP/ADD INDEX` ALTER actions are another broad unresolved family; their conversion is still fail-closed because index and constraint semantics and statement grouping need review. The manifest records per-class applied rule counts and totals.

This refresh addresses the observed DDL syntax blocker in the first emitted migration, but does not establish that the migration batch is runnable. ALTER statements, JSON expressions, dynamic SQL, idempotency behavior, and all other unhandled shapes remain diagnostic flags.

The diagnostic translator also rewrites a double-quoted token to a single-quoted SQL literal only when it immediately follows a comparison operator. This handles MySQL string comparisons such as `loc.code = "de-DE"`; the manifest counts these rewrites under `comparison_double_quoted_literal_to_single_quoted`. Other double-quoted SQL tokens remain flagged as dialect-ambiguous.

The fresh-database run exposed a PostgreSQL `BYTEA` resource returned by DBAL for a language UUID. One verified diagnostic method, `Migration1575021466AddCurrencies::fetchLanguageId()`, now reads stream resources with `stream_get_contents()` and maps failed or empty reads to `null` before its existing fallback logic. The manifest records this single application under `language_uuid_bytea_resource_to_nullable_string`. Other methods with similar names were not changed without an individually verified shape; the default migration registry remains opt-in.

The generated classes and their registry mappings exist only to run one disposable PostgreSQL migration attempt and capture the first failure. The complete class-by-class mapping and unhandled-shape list is in [postgresql-v63-diagnostic-manifest.json](postgresql-v63-diagnostic-manifest.json). Each generated PHP file also carries a diagnostic-only header.

Do not use these mappings for an installed shop. The generator remains fail closed in normal `--inventory` mode; `--diagnostic-inventory` is an explicit best-effort path.
