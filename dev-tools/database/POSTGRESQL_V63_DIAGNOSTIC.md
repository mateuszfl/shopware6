# V6_3 PostgreSQL diagnostic batch

**Diagnostic only. This is not a production-ready PostgreSQL migration port.**

The diagnostic run created registry mappings for all 335 Core V6_3 migrations. It retains 170 existing PostgreSQL variants and 9 audited same-class mappings. It generated 156 best-effort diagnostic variants. The generator flagged unhandled SQL or runtime shapes in 148 of those classes; the remaining 8 have no detected flags but are still unverified. SQLGlot was not invoked.

The first observed PostgreSQL run stopped in `Migration1574695657ProductCrossSelling` with SQLSTATE `42601` at `ENGINE=InnoDB`, after 173 migrations had completed. The refreshed diagnostic output applies CREATE TABLE rules: `BINARY(16)` columns become `BYTEA` with an `octet_length(...)=16` check; `TINYINT[(n)]` becomes `SMALLINT`; `DATETIME[(n)]` becomes `TIMESTAMP[(n)] WITHOUT TIME ZONE`; utf8mb4 column collations become `sw_type_ci`; table-level utf8mb4 defaults are copied to text columns as `COLLATE "sw_type_ci"`; and trailing MySQL engine/charset/collation options are removed. This batch copied the default collation to 31 text columns before stripping the MySQL options. Diagnostic ALTER conversion is scoped to static `ALTER TABLE` statements and rewrites column `BINARY(16)` to `BYTEA CHECK (octet_length("column") = 16)`, `TINYINT[(n)]` to `SMALLINT`, removes `UNSIGNED`, and strips `AFTER` placement while retaining each clause's nullability and default. The latest batch applied those rules to 21 binary columns, 16 tinyint columns, 3 unsigned clauses, and 54 AFTER placements. It also rewrites standalone `ALTER TABLE ... DROP FOREIGN KEY <name>` statements to `DROP CONSTRAINT`, preserving identifier quoting and statement order; the latest batch matched 19 clauses in 15 classes. Multiple `DROP FOREIGN KEY` actions in one ALTER remain unchanged and now receive a specific warning: splitting them would change statement atomicity and could leave only some constraints dropped after an error. The V6_3 source inventory contains seven static index actions: ordinary `ADD INDEX` in `Migration1592466717AddKeywordIndex` and `Migration1596441551CustomerGroupRegistration`; `DROP INDEX` in `Migration1558105657CurrencyPrices`, `Migration1576590301FixSalesChannelDomainLanguageFk`, `Migration1602153572AddSalesChannelIdColumnIntoSalesChannelApiContextTable`, and `Migration1603970276RemoveCustomerEmailUniqueConstraint`; and `DROP INDEX ... ON table` in `Migration1595321666v3`. These cannot be batch-rewritten safely: drops can target explicit indexes, FK-related indexes, or a unique constraint, and splitting/index conversion can alter constraint semantics or statement atomicity. The one observed blocker is handled narrowly: in the diagnostic variant only, `Migration1576590301FixSalesChannelDomainLanguageFk` omits its exact `DROP INDEX fk.sales_channel_domain.language_id` after both foreign keys have been dropped. PostgreSQL does not create MySQL's implicit supporting index for that foreign key, so there is no index to drop; restoring both constraints retains the migration's intended constraints. The other six index actions remain unresolved. The manifest records per-class applied rule counts and totals.

This refresh addresses the observed DDL syntax blocker in the first emitted migration, but does not establish that the migration batch is runnable. ALTER statements, JSON expressions, dynamic SQL, idempotency behavior, and all other unhandled shapes remain diagnostic flags.

The diagnostic translator also rewrites a double-quoted token to a single-quoted SQL literal only when it immediately follows a comparison operator. This handles MySQL string comparisons such as `loc.code = "de-DE"`; the manifest counts these rewrites under `comparison_double_quoted_literal_to_single_quoted`. Other double-quoted SQL tokens remain flagged as dialect-ambiguous.

The latest fresh-database run reached migration 198 of 335 and stopped on MySQL `ALTER TABLE ... MODIFY` syntax in `Migration1580218617RefactorShippingMethodPrice`. The diagnostic translator now converts the exact simple MODIFY forms with supported scalar types into PostgreSQL `ALTER COLUMN ... TYPE`, plus `DROP/SET NOT NULL`; an explicit supported default becomes `DROP DEFAULT` or `SET DEFAULT`, while an omitted default is left untouched. Its BINARY(16) case becomes BYTEA with an explicit length check. Across the V6_3 source inventory, five MODIFY clauses in four migrations were translated. The other MODIFY forms, including JSON and DATETIME declarations and any unsupported shapes, remain flagged in the manifest. This conversion is diagnostic-only and does not change fail-closed `--inventory` behavior.

The latest fresh-database run reached migration 180 of 335 before PostgreSQL reported SQLSTATE `42883` for `JSON_VALID(json)`. A diagnostic-only rewrite now changes the exact DDL form `CHECK (JSON_VALID("column"))` (including backtick-quoted source identifiers) to `CHECK (TRUE)`, retaining the named constraint. The checked fields in all 14 matching migration classes are explicitly declared with the MySQL `JSON` type in their source DDL, which maps to PostgreSQL `json` and already enforces valid JSON syntax. The rewrite is limited to this `CHECK` expression in `--diagnostic-inventory` mode; it does not rewrite arbitrary runtime `JSON_VALID` calls or run in fail-closed inventory mode.
