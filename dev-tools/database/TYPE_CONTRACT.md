# Physical type contract for the PostgreSQL POC

This contract is based on disposable fixture tests against PostgreSQL 18.6 and
MySQL 8.4.11. It governs PostgreSQL DDL and binding work in the DAL adapter and
migrations. Existing MySQL and MariaDB schemas keep their current definitions.
The fixtures do not imply that a complete Shopware schema can yet be installed
on PostgreSQL.

## Binary identifiers and payloads

| Concern | MySQL reference | PostgreSQL decision | DBAL and public result |
| --- | --- | --- | --- |
| ID, FK, `version_id`, mapping ID | `BINARY(16)` | `bytea NOT NULL CHECK (octet_length(column) = 16)` for every non-nullable identifier; nullable identifiers retain `NULL` | Bind scalar with `ParameterType::BINARY`, lists with `ArrayParameterType::BINARY`. PHP holds exactly 16 bytes internally; public IDs remain 32 lowercase hex characters. |
| Composite versioned relation | `(id, version_id)` PK/FK | Both parts are `bytea` with 16-byte checks; FK references both parts | No comparison of a versioned ID without its version where the original relation requires both. |
| Blob, serialized bytes, compressed cart | `BLOB`/`LONGBLOB` | `bytea` without a UUID length check | Bind as `ParameterType::BINARY`; preserve all bytes, including NUL and invalid UTF-8. |

PDO PostgreSQL returns the tested `bytea` columns as streams; PDO MySQL returns
strings. `Uuid::fromBytesToHex()` and `BlobFieldSerializer::decode()` now accept
either representation and consume a stream once. Raw DBAL callers must likewise
normalize a fetched stream before byte operations. Reusing a consumed stream
would produce an empty value. A native PostgreSQL `uuid` column is excluded: it
would require conversion throughout DAL and existing raw SQL. PostgreSQL's
length check prevents the silent padding permitted by MySQL `BINARY(16)`.

## Scalar and JSON types

| Existing shape | PostgreSQL DDL | Binding, hydration, and bounds |
| --- | --- | --- |
| `TINYINT(1)` boolean | `smallint DEFAULT 0 CHECK (column IN (0, 1))` | DAL writes integer `0` or `1`; raw SQL using `= 0` or `= 1` remains valid. Hydrate through the existing boolean serializer. MySQL accepts `2` in the tested column; PostgreSQL rejects it. |
| `DATETIME(3)` | `timestamp(3) without time zone` | Bind a UTC formatted string; fetch has millisecond precision. The database does not apply a host timezone conversion. |
| migration history `TIMESTAMP(6)` | `timestamp(6) without time zone` | Bind UTC strings and keep the DB session at UTC. MySQL `TIMESTAMP` converts through the session timezone, so the reference session must also be UTC. |
| `DECIMAL(p,s)` | `numeric(p,s)` with the original precision and scale | Bind decimal text when exact value matters; return the decimal string until the field's existing serializer applies its PHP type. Do not substitute binary float for money. |
| `DOUBLE` | `double precision` | Preserve approximate numeric behavior only for fields whose MySQL definition is already floating point. |
| unsigned integer | A sufficiently wide signed type plus `CHECK (column BETWEEN 0 AND original_max)`, or `numeric(20,0)` for the full unsigned 64-bit range | The fixture proves the unsigned 32-bit maximum `4294967295` in a PostgreSQL `bigint`. Audit each larger unsigned field before migration; PHP integers and PostgreSQL identity sequences are signed. |
| `AUTO_INCREMENT` | `GENERATED BY DEFAULT AS IDENTITY` on a suitable integer type | Inserts without the column generated `1`, then `2`, on both servers. Use `RETURNING` on PostgreSQL when the caller needs the new value; preserve explicit-value and reset semantics per table. |
| queryable `JSON` | `jsonb` | Bind JSON text. Decode values into the existing PHP structure; object key order and input text formatting are not public contracts. JSON `null` remains distinct from SQL `NULL`. |

JSON duplicate object keys are canonicalized to the last value on both tested
servers. Numeric range is **not** equivalent: PostgreSQL `jsonb` accepts
`1e400` as a number while MySQL 8.4 reports invalid JSON. Do not accept such
payloads solely because PostgreSQL stores them. Validation and JSON path
operations need field-specific tests in later JSON/DAL tasks. A 20-digit JSON
integer can be recovered as a string with `JSON_BIGINT_AS_STRING`, but the
current DAL decoder uses PHP's default JSON decoding and exposes it as an
inexact float on both servers. Consumers needing an exact integer must not
rely on that JSON field. The later JSON adapter must reject non-finite or
out-of-range inputs consistently before PostgreSQL stores values that MySQL
would reject.

## Text comparison and deterministic results

The PostgreSQL candidate for user-facing case and accent insensitive fields is
an ICU, nondeterministic collation:

```sql
CREATE COLLATION sw_type_ci
    (provider = icu, locale = 'und-u-ks-level1', deterministic = false);
```

With PostgreSQL 18.6 and MySQL `utf8mb4_unicode_ci`, the fixture confirms
`café = CAFE`, `Straße = strasse`, `LIKE 'CAF%'` matches `café`, and a unique
column rejects `cafe` after `café`. This is a tested subset, not proof of full
collation equivalence for all Unicode strings. Apply the collation per relevant
column or expression; do not change technical keys, tokens, or binary data to
case insensitive comparison. Record the ICU collation version when creating
indexes, and audit/reindex affected indexes after an ICU version change.

Ascending `ORDER BY value` places `NULL` **last** on PostgreSQL and **first** on
MySQL in the fixture. Queries whose public order matters must specify a `CASE`
for null placement and a stable unique tie breaker. Case/accent equivalent
values can tie under the chosen collation, so collation alone does not ensure a
stable page boundary. Unique fields, `LIKE` patterns, locale-specific matching,
and index use remain per-query review items. PostgreSQL identifiers are limited
to 63 bytes; generated FK/index names must be shortened deterministically and
collision checked when schema generation is implemented.

## Test and implementation boundary

Run the focused fixture test against the isolated databases from
`dev-tools/database/README.md`:

```sh
TYPE_CONTRACT_DATABASE_URL='postgresql://shopware:shopware@127.0.0.1:5433/shopware_pg_test?serverVersion=18.6&charset=utf8' vendor/bin/phpunit --no-configuration --bootstrap vendor/autoload.php tests/integration/Core/Framework/DataAbstractionLayer/Dbal/DatabaseTypeContractTest.php
TYPE_CONTRACT_DATABASE_URL='mysql://shopware:shopware@127.0.0.1:3307/shopware_mysql_test?serverVersion=8.4.11&charset=utf8mb4' vendor/bin/phpunit --no-configuration --bootstrap vendor/autoload.php tests/integration/Core/Framework/DataAbstractionLayer/Dbal/DatabaseTypeContractTest.php
```

The test requires an explicit `_test` database and asserts the server version;
it drops only its own fixture tables and collation. Adapter integration, actual
schema generation, migration translation, JSON queries, and broader raw SQL
callers remain with the later tasks. No release or upgrade note is needed for
this internal POC contract and binary hydration fix: it introduces no released
database configuration or migration path for external users yet.
